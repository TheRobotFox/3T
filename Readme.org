** Callable
   Callable has Environment which inlcudes its arguments
   Arg Pattern is matched against by Interpreter and Environment bindings for args are overwritten
   
  - Closure :: All arguments are evaluated before passed into Environment
    returns expression
  - Macro :: Aguments are lifted into cons before passed into Environment
    returned Form is evaluated
* Optimizations
  - Byte-Compile
  - Eval Const Expressions and Inline Macros -> when not dependent on value of arguments
  - Use Lists insead of Concells for code
  - Expressions -> use polymorphism with GC +Arena+ allocation
  - Only have global Scope and local scope overlays (as vectors?)
    
* Memory Sections
  Employ different Memory sections to aid Garbage Collection

  Idealy Memory is relocatable, aim for mark/sweep
  Pointers need to be visible to GC
  
** Module
   Storage page for Loaded [[Module]]s, which includes
   - Static Data (Cons, strings)
   - Byte Code
   - Symbols

   Constant Memory Section, will not be changed after creation and be
  freed upon module unload

   (Section will be loaded on restart no relocation required)
** Cons
   Storage for Cons cells

   In most cases Cons cells will be in a hierachy List/Tree like
   structure => Maybe Group cons cells by dependence eg. free whole
   page Either create runtime overhead or employ partial gc merging
   cons into blocks, can be done semi asyn
** Stack
   Callframes, function stacks

   - Reclaim as much memory as possible while not impacting runtime performance
   - used by byte compiler
